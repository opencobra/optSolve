## Findings per principle

**I. Performance And Memory First.** Conforms. Input is borrowed with no allocation proportional to
nnz; the only C-layer allocations (cone descriptors, raw-parameter names, lazy name copies, NaN
fill) are bounded and listed in Complexity Tracking (plan.md:50-58, 303-307). Environment reuse is
User Story 2, tested in T012. The solver configuration audit covers the one new parameter,
`SoftMemLimit` (plan.md:59-61, research R9). Validation is not removed (plan.md:57). Performance
targets SC-002 and SC-003 are tasked in T017.

**II. Testing, Benchmarks, And Behavioural Evidence.** **Violation V1** (one specified result
field and its option have no planned check). Otherwise conforms: both tiers, licensed tests in
`harness = false` targets with visible skips (tasks.md:7-12); tests written once over the shared
registry (T010, T015); the comparison rule implemented once in `tests/common/compare.rs` with
negative cases (T003); every C-layer check has a failing-input test (T006) and every expressible
Rust-API invalid input is mapped (T016), with "before any solver call" shown by the
environment-creation count (T016); the QP upper-triangle case exists in
`tests/contract/qp_conic.rs:258` and is therefore in T016's mapping; behavioural integration
evidence through C programs linked against the built libraries (T010, T018).

  (Principle II, "Every behavioural change MUST include the narrowest practical check";
  Development Workflow; VI traceability).**
  - Required: FR-005 "the certificate when requested" (spec.md:339); FR-004 lists `certificates`
    among the options (spec.md:332); FR-014 compares "every result field"; the contract defines
    `optsolver_result_certificate`, `optsolver_result_certificate_array`,
    `OPTSOLVER_CERTIFICATE_*` and `OPTSOLVER_CERT_Y/_Z/_S/_RAY` (contract:73-75, 156, 224-225).
  - Both backends support certificates (src/gurobi/solve.rs:45, src/mosek/solve.rs:39), and the
    Rust API already has a certificate test (tests/common/f002.rs:23-45).
  - No task requests a certificate through C: T010's non-optimal toys are checked "as a status"
    only (tasks.md:116); T008 checks accessors "on a toy LP" (tasks.md:100-101), where the
    certificate is absent; T005's code-by-code enum list (tasks.md:70-72) omits the certificate
    kind. A swapped Farkas/ray mapping or array selector would pass every planned test.
  - implementation-review.md:39 maps FR-005 to T008, T010, T015 as covered.
  - **Repair** (tasks.md and implementation-review.md only): add to T010 (or T008) a licensed
    trial that sets `certificates` = 1 through C on the infeasible and unbounded toy instances and
    compares the certificate kind and every certificate array (`OPTSOLVER_CERT_Y`, `_Z`, `_S`,
    `_RAY`) with the Rust API's by the comparison rule; add the certificate kind to T005's
    code-by-code list; correct the FR-005 row of the coverage table.

- **V2. Two guards this feature adds are not exercised against the failure they guard (XV-C,
  "Any check, gate or comparison harness MUST be exercised against the failure it guards";
  tasks-template T010g; XIV-D for the null finding).**
  - The shared driver runner "asserts empty standard output and error on every run"
    (tasks.md:43-44). No task shows it detects a program that does print. If capture were

  - The leak check: "the program runs under AddressSanitizer's leak checker with zero leaks"

    (a deliberately leaked allocation reported).
  - **Repair** (tasks.md): in T003, a runner self-test with a C program that writes one byte to

    a deliberate leak under the same sanitizer configuration and requires the leak to be reported
    (if the sanitizer is unavailable, both are recorded unverified, as T016 already says).

- **V3. `unsafe` outside `src/capi/` is required by the tasks but excluded by the plan, and the
