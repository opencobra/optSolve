## Violations

- **V1. The "too large" dimension case is not covered, and the analysis overstates the
  error-handling criterion's coverage (Development Workflow; Principle II; review instruction
  "every requirement and success criterion is covered by tasks"; "the analysis is honest").**
  - SC-006 (spec.md:481-484): "Every invalid-input case of the existing Rust failing-input tests
    that a C caller can express returns the 'invalid input' (or 'too large') code with a message
    naming the input, before any solver call". The spec's Edge Cases (spec.md:287-288): "A
    dimension above what the solvers accept (row or column count beyond the 32-bit limit): the
    'too large' error, as in the Rust API."
  - The only existing Rust failing-input test returning "too large" is
    `t020_dimension_too_large` (tests/contract.rs:313-328: `CscRef::new(MAX_DIMENSION + 1, …)` →
    `TooLarge { what: "m" }`, and the same for n). It does not use `expect_invalid`.
  - T016 operationalises SC-006 as "each `expect_invalid` case of `tests/contract.rs` mapped to a
    C call, or recorded as not expressible from C with the reason" (tasks.md:181-183). None of
    the 38 `expect_invalid` uses returns "too large", so the case the parenthetical "(or TOO_LARGE)"
    exists for is neither mapped nor recorded. T006's TOO_LARGE tests cover only the C layer's own
    overflow checks (`cols + 1`, nnz, tasks.md:93, 99), not the Rust API's 32-bit dimension limit.
  - It is not a formality: from C, a declared `rows` or `cols` above `i32::MAX` comes with
    caller arrays whose declared lengths derive from those dimensions (contract 121-131). Whether
    the case can be posed soundly without gigabytes of caller memory depends on the C layer
    building and validating A before slicing the row data, an order the contract does not state.
    That is exactly what the task must either test or record as not expressible, with the reason.
  - implementation-review.md:60 claims SC-006 is covered by "T016 (every expressible invalid
    input …)".
  - **Repair** (tasks.md and implementation-review.md only): add `t020_dimension_too_large` (rows
    and cols each `MAX_DIMENSION + 1`) to T016's mapping — either a C call returning
    `OPTSOLVER_ERR_TOO_LARGE` naming the dimension before any environment is created (stating the
    order in which the C layer builds A and the row data, if that is what makes it expressible),
    or a recorded "not expressible from C" with the reason — and correct the SC-006 row of the
    analysis.

- **V2. The link demonstration is ordered before the documentation it must use (Development
  Workflow, ordering; review instruction "the proposed implementation scope is coherent").**
  - SC-007 (spec.md:485-487): "A minimal C program built … using only the compile and link flags
    the documentation states". T018 (tasks.md:206-207): "compile and run with the documented
    flags". The flags are written only in T019 (tasks.md:211-213: "building; compile, link and
    run-time flags"), which the dependency order places after T018 ("benchmarks and link
    demonstration (T017–T018) → polish and closeout (T019–T022)", tasks.md:228-229). T002 states
    that T019 writes the prose sections (tasks.md:32-33); the header only points to them (T004).
    The static library's native-library list is discovered only during implementation
    (research R4, lines 113-116).
  - Followed in order, T018 either demonstrates flags no document yet states (not SC-007's
    evidence) or must perform part of T019 out of order.
  - **Repair** (tasks.md, and implementation-review.md if it restates the order): move the
    building-and-linking part of the interface document into T018 (or a task before it), or
    order T018 after T019's flags section and say so in the dependency line.
