### VII. Rust And FFI Coding Standards

**Partly conforms. One defect (finding 1).**

- **VII-A.** `unsafe` is confined to `src/capi/`, admitted as an FFI module (plan.md:78-79,
  135-137). Every block carries `SAFETY`, and every `pub unsafe extern "C" fn` carries `# Safety`.
- **VII-B: ownership and lifetimes.** Handles are `Box`ed, opaque, and freed by one function each.
  `Env` lifetimes are unchanged.
- **VII-B: `Send` for `mosek::Env`.** Supported by §10.3 and §10.6: one environment is used by
  `MSK_optimize` from different threads.
- **VII-B: `Send` for `gurobi::Env`.**
  - Supported for use on another thread: "Pass each additional thread an initialized environment
    for its exclusive use".
  - Not supported for deletion on a non-main thread. The artefacts now mark this explicitly as an
    unverified inference resting on the preceding sentence ("creation and deletion are not
    thread-safe"). They mitigate it with a lock and a licensed test, and the `SAFETY` comment is to
    record it.
  - I accept this reading. Read as a whole, the article gives non-thread-safety as the hazard,
    which a process-wide lock excludes. The residual risk is stated, not hidden.
  - That argument holds only if every creation and freeing in the process takes the lock. As
    planned, two do not (finding 1).
- **VII-C.** Errors are codes; `catch_unwind` runs at every entry point; the `panic = "abort"`
  case is documented (plan.md:114-118).
- **VII-D.** The C layer's null and row-form checks run before slices are built. The Rust API's
  validation is otherwise reused.
- **VII-E.** No vendor declaration is added.
- **VII-F.** Lints, `links` and build-script variables are unchanged. No profile is relied on.
- **VII-G.** `SoftMemLimit` is set only in `gurobi::params::apply` and is listed in `MAPPINGS`, so
  the conflict rule covers it. The C layer is forbidden to reach `*.params` and `*.ffi`
  (architecture-delta.yaml:89-91).

**Finding 1 (VII-B, with V and XIII-C): the Gurobi creation and freeing lock does not cover every
site, so the argument for `Send` would be false as planned.**

The plan places the lock at these sites:
- `Env::new` and `Drop` (research.md:63-66: "held across `GRBemptyenvinternal` … `GRBstartenv` in
  `Env::new` and across `GRBfreeenv` in `Drop`");
- `gurobi::load` model creation and freeing;
- the `gurobi::callback` test helper (plan.md:83-84, 256-258; architecture-delta.yaml:49-55).

The code has two further sites that create and free Gurobi environments outside `Env::new` and
`Drop`:
- `src/gurobi/env.rs:160-165`, test `empty_environment_is_created_and_freed_without_licence`. It
  calls `empty()` (`GRBemptyenvinternal`) and then `ffi::GRBfreeenv` directly.
- `src/gurobi/params.rs:389-396`, test
  `configure_new_environment_sets_output_flag_zero_before_start`. It does the same through
  `env::empty()`.

`empty()` is `pub(crate)` (`src/gurobi/env.rs:63`), so any crate code can reach an unlocked
creation.

Library unit tests run on several threads in one process. These two tests would therefore create
and free environments concurrently with licensed tests that create environments under the lock.
This includes the planned licensed concurrency test if it lives in the library test binary. That
is exactly the unserialised creation and deletion the vendor calls not thread-safe.

The research claims the lock "closes a hazard that existed before" and that it serialises creation
and freeing process-wide. That claim would then be false in the very process whose clean run is
offered as the evidence for the accepted risk. Review 2's repair extended the lock to the callback
test helper but missed these two sites. Neither `gurobi.params` (whose delta entry names only the
`SoftMemLimit` mapping) nor the env.rs tests appear in the planned change scope.

**Repair:** state the lock as a rule over every call of `GRBemptyenvinternal`, `GRBstartenv`,
`GRBfreeenv`, `GRBXloadmodel` and `GRBfreemodel` in the crate, tests included, and make the rule
checkable. Two ways to do this:
- route those calls through one locked helper in `gurobi::env`;
- or have `empty()` require a guard token from the caller. Note that `std::sync::Mutex` is not
  re-entrant, and `Env::new` already holds the lock across `empty()` and `start`.

Then:
- add the two test sites, through `gurobi.params` and `gurobi.env`, to the delta and the plan's
  Project Structure;
- route to tasks a source-text check, like the existing setter test in `tests/standards.rs`, that
  those symbols are called only under the guard;
- decide what a poisoned lock does (a panic while it is held) and record it.

## Verdict

**REVISE_ARCHITECTURE (FAIL).**

The requirements stand. The architecture is sound and close to approval:
- the names are approved;
- the reuse assessment is complete;
- there is no duplication;
- reachability and adoption are in order;
- the ADR now agrees with the delta.

One defect is substantive. The process-wide Gurobi lock, on which the `Send` argument and its
accepted risk depend, is planned for only some of the sites that create and free Gurobi
environments. Two existing unit-test sites, reached through the `pub(crate)` function `empty()`,
would remain unserialised in the same process as the planned concurrency evidence.

**Binding constraint**: every call of `GRBemptyenvinternal`, `GRBstartenv`, `GRBfreeenv`,
`GRBXloadmodel` and `GRBfreemodel` in the crate, tests included, is made under the one lock, by a
rule the delta states and a test checks.

### Violations and repairs

1. **Lock coverage (VII-B, V, XIII-C).**
   - State the lock as a rule over all five symbols, crate-wide.
   - Choose a non-re-entrant-safe mechanism: a locked helper, or a guard token required by
     `empty()`.
   - Add `src/gurobi/env.rs` tests (lines 160-165) and `src/gurobi/params.rs` tests
     (lines 389-396) to the delta (`gurobi.env`, `gurobi.params`) and to the plan's Project
     Structure.
   - Route a source-text check (as in `tests/standards.rs`) to tasks.
   - Record the behaviour on a poisoned lock.
2. **Keys in place of names (XII-A).** plan.md:125 and plan.md:266: put the descriptive name beside
   each key.
3. **Wrong cross-reference.** plan.md:58: "research R8" should be "research R9 (solver
   configuration audit)".

After these repairs a new reviewer with a fresh context reviews the result (VI-A). Nothing else in
this review blocks `APPROVE_WITH_ADR` once they are made.

  - The contract's thread rule (c-interface.md:150-152) says nothing about creating MOSEK

  - Research marks MOSEK creation thread-safety unverified (research.md:66-68) and justifies the
