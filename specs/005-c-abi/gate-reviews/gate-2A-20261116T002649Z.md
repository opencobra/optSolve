## Verdict

**REVISE_ARCHITECTURE (FAIL).**

The requirements stand. Most of the architecture is sound and need not change:

- the translation-only `capi` layer in the one crate;
- edges only into the core and the backends;
- `Send`, not `Sync`, with a compiler-enforced Gurobi lifecycle lock;
- the silent panic hook;
- the memory limit as a solver-independent option;
- the names;
- ADR-0004.

The two findings below concern the components the feature adds to verify itself. They are
grounds for `REVISE_ARCHITECTURE` under XIII-C (semantic duplication; reachability). The repairs
are to the plan, delta and research text only.

### Violations and repairs

1. **Reuse and duplication for the test and benchmark components (V, Spec-Driven Scope Control
   And Reuse; II, one shared test module; XIII-C, semantic duplication; consistency between
   the delta, plan and research).**
   - *Defect, part (a): the comparison rule.* The three artefacts disagree:
     - the delta says `test.harness` gets a writer and reader with the "comparison reused
       unchanged" (architecture-delta.yaml:55);
     - research R7 says the C result is compared "through the shared comparison helpers"
       (research.md:193);
     - the plan says the spec's tolerance rule is "implemented once in the shared test module
       (`tests/common/cdata.rs`)" (plan.md:101-102).

     The existing helper `compare::judge` (`tests/common/compare.rs:85-125`) compares only
     status and objective and requires both reports Verified. It cannot implement the spec's
     rule (every vector entry, limit reason, failed-measure names). So either the comparison is
     not reused, or the rule is not implemented. The new rule is also a close relative of
     `toy::objectives_agree` (`tests/common/toy.rs:203-205`; ten times the tolerance, scaled by
     max(1, min(|a|, |b|)), where the spec scales by max(1, |Rust value|)). The plan neither
     inspects it nor records the second predicate.
   - *Defect, part (b): C compiler discovery.* The repository already compiles C test programs
     with the `cc` crate, in two copies of the same helpers (`host_triple`, `manifest_dir`, the
     `cc::Build` configuration): `tests/header_conformance.rs:20-75` and
     `tests/header_conformance_mosek.rs:21-66`. `test.c_interface` needs the same capability,
     plus linking and running. The plan does not name this as existing code. It says neither
     whether the helper goes into the shared test module (II: "no test re-implements it") nor
     whether a third copy is accepted and why.
   - *Defect, part (c): benchmark machinery.* `bench.load_solve` owns "per-phase timing and
     dedicated-process memory measurement, per backend" (components.yaml:102-104). It holds the
     child-process-per-scenario launcher, the `dhat` global allocator, and the
     `commit`/`machine`/`profile`/`median_and_spread` provenance and statistics helpers
     (`benches/load_solve.rs:232-295, 376-460, 606-660`). `bench.c_interface` needs all of these.
     The plan does not name the owner. It records none of these dispositions:
     - extending `benches/load_solve.rs` with C-path scenarios (a smaller conforming
       alternative);
     - extracting the helpers into the shared module the benchmark already includes
       (`#[path = "../tests/common/mod.rs"]`);
     - duplicating them, with a reason.
   - *Repair*:
     - Add to the reuse and adoption assessment, proportionately, the owning component,
       inspected `file:line` and disposition for each of (a), (b) and (c), and list any
       duplication left in place with its reason.
     - Make the delta's `test.harness` entry, research R7 and the plan say the same thing about
       the comparison rule: a new predicate in the shared module, related to or replacing
       `objectives_agree` as decided.
     - If the decision is to extend `bench.load_solve` instead of adding `bench.c_interface`,
       update the delta's components accordingly.

2. **Reachability of the private `capi` module from the components that test and benchmark it
   (XIII-C, reachability; XIII-E; delta completeness).**
   - *Defect*: the plan states that "the module is private in Rust (no Rust visibility change)"
     (plan.md:231-233). Yet:
     - research R6 has the licence-free integration test `tests/c_interface.rs` compare the C
       program's `sizeof`, `offsetof` and constants "with the Rust `size_of`, `offset_of!` and
       constants" (research.md:178-183). An integration test is a separate crate and cannot name
       private `#[repr(C)]` types, fields or constants, so the test cannot be written as
       specified;
     - the heap criterion (SC-002) measures the C path with `dhat`, which sees only allocations
       through the Rust global allocator of its own process. The plan does not say how
       `benches/c_interface.rs` reaches the C path in-process: `extern "C"` declarations of the
       exported symbols, linking `liboptsolver.a`, or a separate C process (which `dhat` could
       not measure);
     - the delta declares no edge from `bench.c_interface` at all, and declares only
       `test.c_interface → capi.header`, although both link against and call the `capi` library
       (architecture-delta.yaml:67-76).
   - *Repair*:
     - Decide where the layout and constant comparison runs, and record it in research R6, the
       plan's reachability bullet and the delta. Two options:
       - a unit test inside `src/capi/`, which can see the private types, while the integration
         test keeps the prototype comparison and C execution;
       - making the `#[repr(C)]` types reachable, which is a public-interface change to be
         declared in `public_interfaces_changed`, with its documentation and drift-test
         consequences.
     - State how the benchmark reaches the C path so that the heap profiler measures it.
     - Declare the edges `test.c_interface → capi` and `bench.c_interface → capi` (and to the
       core, backends and test harness as used).

### Observations routed to tasks (not conditions of this verdict)

- **Order of operations (II, FR-014)**: unlicensed tests under `--features capi` (no backend)
  must observe "invalid input" for Rust-API validation through C. The solve entry points must
  therefore build and validate the `Problem` and translate the `Options` before resolving the
  backend or creating an environment, including in `optsolver_solve_once`. State the order in
  the contract.
- **Size bounds (VII-D)**: apply the bound `length · sizeof(element) ≤ isize::MAX` to every
