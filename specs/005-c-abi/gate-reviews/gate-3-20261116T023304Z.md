## Findings per principle

### I. Performance And Memory First — violation (see V-5)

The input path is zero-copy by construction:
- `borrow` (`src/capi/problem.rs:189-209`) wraps `slice::from_raw_parts`, and every input array
  goes through it (`problem.rs:327-448`).
- Only the cone list and the power-cone exponents are copied (`problem.rs:275-319`). These are
  small descriptors that FR-003 allows.

The result path reads owned arrays in place (`result.rs` `optsolver_result_array`). Names are
converted lazily (`result.rs:51-62`). Caller buffers are NaN-filled with no allocation
(`result.rs` `out_array`). This matches the plan's Complexity Tracking.

Environment reuse is shown by `t012::reuse_one_handle` (20 problems, one environment).

Solver configuration audit: the only new parameter is `SoftMemLimit`, unset by default and
documented (research R9, `src/options.rs:119-123`).

The violation: the heap and wall-time evidence covers fewer accessors than claimed (V-5).

### II. Testing, Benchmarks, And Behavioural Evidence — violations V-1, V-2, V-4, V-6

What complies:
- Both tiers exist, and licensed trials are skipped visibly. With `capi` only, the 20 licensed
  trials are ignored with a reason.
- Tests are written once over the shared registry (`t010`, `t015` iterate the toy registry).
- The comparison rule is implemented once (`tests/common/compare.rs:388-470`). It is tested
  against its failures, including "everything failed is uninterpretable" (`compare.rs` self
  tests `t003::agreement_*`).
- Failing-input tests exist for the C-layer checks:
  - `problem.rs` tests `c_layer_checks_name_the_field` and
    `dimensions_are_checked_before_any_array`;
  - `tests/c/errors.c` covers NULL top-level pointers, too-large dimensions, truncated options
    and the panic;
  - `t016::invalid_inputs_through_c` maps every `expect_invalid` case of `tests/contract.rs` to
    C, or records why it is not expressible (`c_interface.rs:631-636`).
- Behavioural integration: real C programs are linked against the built libraries. The
  memory-limit trial reaches `StoppedAtLimit`/`Memory` with a no-limit control
  (`c_interface.rs:1354-1399`, `contract/f005.rs:169-201`).

The violations:
- **V-1**: the licensed tier does not pass reliably at the reviewed commit.
- **V-2**: the pointer-identity positive control covers only some arrays.
- **V-4**: bit-identity is not reported for conic and certificate trials.
- **V-6**: Gate 2 routed a regression comparison against recorded results (observation O3), and

### VII. Rust And FFI Coding Standards — violation V-3

What complies:
- VII-A:
  - `unsafe` appears only in FFI modules (`tests/standards.rs` `FFI_MODULES`);
  - non-FFI modules keep `#![forbid(unsafe_code)]`;
  - `SAFETY` comments are present (clippy `undocumented_unsafe_blocks` denied, passes);
  - public `unsafe extern "C"` functions carry `# Safety`.
- VII-B: `unsafe impl Send` for both `Env` types cites vendor documentation
  (`src/gurobi/env.rs:26-37`, `src/mosek/env.rs:27-35`). The Gurobi lifecycle lock is enforced by
  the `Lifecycle` token (`env.rs:39-67`) and a source test with a negative case
  (`standards.rs` `lifecycle_check_catches_a_stray_call`). Handles are `Box`ed and freed once.
- VII-C:
  - every entry point is inside `guard`/`contain`, enforced by
    `every_c_entry_point_contains_panics` with a negative case;
  - non-optimal outcomes are statuses.
- VII-D: the problem is built and validated before environment creation in
  `optsolver_solve_once` (`result.rs:212-221`).
- VII-E: no new vendor declarations.
- VII-F:
  - lints are unchanged, and the `links` key and build script are unchanged;
  - lint allowances are scoped per item;
  - the MSRV build passes.
- VII-G: the C layer sets no parameter. `SoftMemLimit` is set only in `gurobi::params::apply`
  (`params.rs:242-246`) and listed in `MAPPINGS`, so the conflict rule covers it, as tested by
  `f005::t013_memory_limit_option`.

The violation:
- **V-3 (VII-A, VII-D)**: `optsolver::capi::solve_lp_through_c` (`src/capi/result.rs:907`) is a
  safe `pub fn`, re-exported through the `pub` module `optsolver::capi`. It takes `CPathLp`,
  whose fields `m` and `n` and the slices are all public and unchecked against each other. It
  then calls `optsolver_solve` / `optsolver_solve_into` under the comments "SAFETY: every
  pointer refers to live Rust data for the call" (`result.rs:952, 974`).
  - The C layer slices `b_l`, `b_u` by `m`, slices `c`, `l`, `u` by `n`, and slices `col_ptrs`
    by `n + 1` (`problem.rs:340-391`).
  - So safe code such as `CPathLp { m: 1000, b_l: &[0.0], … }` causes out-of-bounds reads:
    undefined behaviour reachable from safe Rust.
  - The SAFETY argument names an invariant that nothing establishes. An unchecked entry exists
    without being an `unsafe fn` with a `# Safety` contract (VII-D).

## Violations and repairs

1. **V-1: the licensed C tests race, and the in-gate claim does not reproduce.**
   - Principles: II, Development Workflow And Quality Gates.
   - Cause: `t016::leak_check_licensed::gurobi` and `::mosek` each recompile the same
     executable path `driver-Static-san` through the uncached `cdata::program`
     (`cdata.rs:557-604, 719-721`, `c_interface.rs:1451-1455`). One test executes it while the
     other is relinking it, which fails with ETXTBSY (6 of 7 runs here).
   - Consequence: the receipt's claim that all combinations pass the test suite does not hold
     reproducibly at `11647b1`.
   - Repair: build each sanitized program once per process, cached in a `OnceLock` like
     `driver()`, or give each build a unique path. Re-run the in-gate checks at a committed
     revision.
2. **V-2: the pointer-identity positive control is incomplete.**
   - Principles: II, XIV-D; spec User Story 2 scenario 1; task T006.
   - Gap: `every_slice_is_the_callers_array` (`problem.rs:684-723`) does not cover `row_sense`,
     `b`, Q's three arrays, F's three arrays, or `g`.
   - Repair: extend the test to every slice.
3. **V-3: UB is reachable from safe code.**
   - Principles: VII-A, VII-D.
   - Location: `solve_lp_through_c` / `CPathLp`.
   - Repair: validate that each slice length agrees with `m`, `n` and `col_ptrs[n]` before
     building the C structure (or derive `m` and `n` from the slices), or make the function
     `unsafe fn` with a `# Safety` contract. Then correct the SAFETY comments.
4. **V-4: bit-identity is not reported for conic and certificate trials.**
   - Principles: spec SC-001 and Clarifications ("a difference within the bound is accepted but
     recorded"), II.
   - Gap: `t015_conic_toys` and `t010_certificates` discard the `Ok(false)` result.
   - Repair: count and report bit-identity, and record any within-bound difference, as `t010`
     does.
5. **V-5: the benchmark claims cover fewer accessors than stated.**
   - Principles: XV-A, I; task T017; spec SC-003.
   - Repair: make the helper read every accessor (names, raw statuses, parameters, attributes,
     measures, basis, certificate) and re-measure. Alternatively narrow the claims and the
     task to what is measured.
6. **V-6: the replaced wall-time evidence and the regression check are missing.**
   - Principles: XV-A, IX-E, II.
   - Repair:
     - restore or re-run, and bundle, the separate-process wall-time runs;
     - report them with N and spread beside the alternating runs, and record the method change
       and its reason in `human-loop.md`;
     - state whether N = 5 resolves the 1 ms criterion given the spread;
     - perform the Rust-path regression comparison against the feature-003 bundle and record
       it, or state why the runs are not comparable.
7. **V-7: CHK015 is still open at its gate (VI-B).**
   - Repair: mark CHK015 resolved, citing the evidence for each success criterion, or accept it
     open with a rationale (for example the consumer's `runmat mex` demonstration) in
     `human-loop.md`.
8. **V-8: history prose sits inline (XII-B).**
   - Repair: move the history in `src/gurobi/solve.rs:84-85` and `tests/common/ccompiler.rs:1-3`
     to a History section at the end of each file.
9. **V-9: the benchmark bundles are incomplete (XIV-A, XIV-B).**
   - Repair: record in every C-path bundle the effective parameters, the solver versions, the
     instance's dimensions and nonzeros, and a tree identity (a commit, or commit plus content
     hash).
10. **V-10: the Gurobi version is restated in code (Governance, Project Parameters).**
    - Repair: derive the Gurobi library name in `cdata.rs` from `project.yml`, or from a value
      `build.rs` exports. Replace the restatement in `docs/llm-interface.md` with a pointer.
