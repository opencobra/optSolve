## Findings per principle

### I. Performance And Memory First

**Conforms.**
- The input path makes no copy: arrays are borrowed through `slice::from_raw_parts` (plan.md:49-55,
  research R5). The C layer allocates only two things:
  - the cone descriptors, including power-cone exponents. This is needed because the Rust `Cone`
    owns `alpha: Vec<f64>` (src/conic.rs:34, 41).
  - the raw-parameter `String`s. This is needed because `Options::raw` is
    `Vec<(String, ParamValue)>` (src/options.rs).

  Neither allocation is proportional to nnz.
- The NaN fill and the name copies are listed in Complexity Tracking (plan.md:269-270).

- Solver configuration audit: research R2/R9 audits the only new parameter. I checked the vendor

  - That reference states no "set before the environment starts" restriction for `SoftMemLimit`.

### VII. Rust And FFI Coding Standards

**Partly conforms; one defect (repair 1).**
- **VII-A**: `unsafe` is confined to `src/capi/`, which is admitted as an FFI module. Every block
  carries `SAFETY` and every `pub unsafe extern "C" fn` carries `# Safety` (plan.md:76-78).
- **VII-B**: `unsafe impl Send` (not `Sync`) is planned for both `Env` types on vendor evidence. I
  verified the evidence:
  - MOSEK `capi.pdf` §10.3 (lines 9574-9575 of the text extraction) says verbatim: "Sharing a task
    between threads is safe, as long as it is not accessed from more than one thread at a time.
    Multiple tasks can be created and used in parallel without any problems".
  - The `MSKcallbackfunc` prohibition is at text lines 35042 and 35142.

  The earlier deferred-`Send` rulings are superseded with their grounds recorded.
- **VII-C**: errors are codes and panics are contained at every entry point. The
  `panic = "abort"` case is documented (plan.md:110-114).
- **VII-D**: null and length checks run before slices are built; otherwise the Rust API's own
  validation applies.
- **VII-E**: no vendor declaration is added.
- **VII-F**: the `links` key and the build-script variables are unchanged. The crate types are
  unconditional (research R4); this is acceptable.
- **VII-G**: `SoftMemLimit` is set only in `gurobi::params::apply`. The C layer is forbidden to
  reach `*.params` and `*.ffi` (delta lines 128-130).

**The defect (VII-B, together with XIII-B and XIII-C below): where the Gurobi creation and freeing
lock lives is stated inconsistently.**
- The spec that passed Gate 1 places it in the Gurobi backend: spec.md:85-87, "serialised by one
  process-wide lock in the Gurobi backend".
- The delta places it in `gurobi.env`: architecture-delta.yaml:91-92, "process-wide lock
  serialising environment creation and freeing".
- research.md:61-64 agrees: "`gurobi::env` gains one process-wide `Mutex<()>` held across
  `GRBemptyenvinternal` … `GRBstartenv` in `Env::new` and across `GRBfreeenv` in `Drop`".
- But other artefacts place it in the C layer:
  - ADR-0004 decision 5 (ADR line 31-32): "Gurobi creation and freeing are serialised in the C
    layer".
  - research.md:47-48, the R3 Decision line: "serialised inside the C layer by one process-wide
    lock".
  - plan.md:246, `src/capi/env.rs`: "environment handle, Gurobi creation lock". plan.md:249 also
    lists the lock in `src/gurobi/env.rs`.

The location is not a detail. `Env` becomes `Send` for Rust callers too (FR-021), so a lock held
only in the C layer would leave Rust callers creating or dropping Gurobi environments concurrently
on several threads. The vendor says that is unsafe (support article 360043111231, quoted in R3). It
would also make the `unsafe impl Send` unsound for Rust callers. The ADR is the durable record, and
it would become Accepted on approval with the wrong decision in it.

maintainer decision. XII-B (historical prose) does not apply at the planning stage.

## Verdict

**REVISE_ARCHITECTURE (FAIL).**

The requirements stand. The architecture is sound in substance: the names are approved, the reuse
assessment is complete, there is no duplication, and reachability and adoption are in order. But
the delta's accompanying records are inconsistent with the delta and with the approved spec on
where the Gurobi lock lives, and an ADR cannot be accepted while it records the wrong decision.

**Binding constraint**: the Gurobi environment creation and freeing lock belongs in the Gurobi
backend (`gurobi.env`: `Env::new` and `Drop`), not in the C layer, because `Env: Send` is a Rust
API change that Rust callers rely on too.

Violations and repairs:

1. **Location of the Gurobi lock (VII-B, XIII-B, XIII-C).** Repair:
   - ADR-0004 decision 5: say creation and freeing are serialised inside `gurobi::env`.
   - research.md R3 Decision (lines 47-48): say the same.
   - plan.md:246: remove "Gurobi creation lock" from `src/capi/env.rs`, leaving `src/gurobi/env.rs`
     as the only home.
2. **Plan does not match the delta (XIII-C).** Repair in plan.md "Proposed delta" (lines 162-167):
   - List the edges `capi → gurobi.solve, mosek.solve` (through `Backend`) as the delta does,
     instead of "environment creation only".
   - Include `gurobi.solve` among the modified components.
3. **Symbols outside the inventory (XII-C, Notation Convention).** Repair:
   - contracts/c-interface.md:17-18: state the compatibility rule in words, as FR-015 does.
   - plan.md:50, research.md:110, data-model.md:16: replace `p`, for example "one descriptor per
     cone (`num_cones`)".
   - contracts/c-interface.md:84: replace `r` with the field name `order`.

After these repairs a new reviewer with a fresh context reviews the result (VI-A). Nothing above
blocks an `APPROVE_WITH_ADR` once they are made.
