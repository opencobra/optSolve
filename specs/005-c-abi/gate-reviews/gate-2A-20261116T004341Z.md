## Vendor evidence (constitution VII-B, VII-E, X)

- **MOSEK** (capi.pdf):
  - §10.3 reads: "Sharing a task between threads is safe, as long as it is not accessed from more
    than one thread at a time. Multiple tasks can be created and used in parallel without any
    problems".
  - §10.6 reads: "Calling MSK_optimize from different threads using the same MOSEK environment
    only consumes one license token".
  - The `MSKcallbackfunc` entries read: "The user must not call any MOSEK function directly or
    indirectly from the callback function".
  - All three match research R1 and R3 verbatim.
  - `mosek.h` 11.2 declares no memory-limit parameter. Its memory items are
    `MSK_IPAR_MIO_MEMORY_EMPHASIS_LEVEL`, `MSK_RES_TRM_SERVER_MAX_MEMORY`, `MSK_getmemusagetask`
    and `MSK_checkmemtask`, a memory-debugging check that research R1 does not list. None of these
    is a limit, so the finding stands.
- **Gurobi**:
  - `gurobi_c.h` 13.0.3 declares `GRB_MEM_LIMIT 17`, `GRB_DBL_PAR_MEMLIMIT "MemLimit"` and
    `GRB_DBL_PAR_SOFTMEMLIMIT "SoftMemLimit"`.
  - The 13.0 parameter reference's `SoftMemLimit` entry gives type double, default Infinity and
    minimum 0. Each sentence quoted in research R2 and spec SC-005 matches, including
    "termination may be non-deterministic for multi-threaded runs" and "allocated memory is
    tracked across all models within a Gurobi environment".
  - Support article 360043111231 says, verbatim: "Gurobi's environment creation and deletion are
    not thread-safe", "In a multithreaded application, create and delete environments in the main
    thread", and "Pass each additional thread an initialized environment for its exclusive use".
  - The C-reference sentences come through feature 001 research R17-7, checked 2026-11-14. I could
    not fetch the page again (the URL I tried returned 404), so I rely on that dated record. That
    record also states that "a later `Send` (not `Sync`) `Env` would also need creation serialised
    by a lock". The present design is therefore the one the earlier ruling anticipated.

## Findings per principle

**I. Performance and memory first: complies.**
- **Input path**: inputs are borrowed through `slice::from_raw_parts` with no copy (plan.md:50-58;
  research R5).
- **Allocations**: the C layer allocates only these, none proportional to nnz:
  - the cone descriptor vector, O(`num_cones`) ≤ O(k), with power-cone exponents. These are
    copied because the Rust `Cone` variants own `alpha: Vec<f64>` (`src/conic.rs:30-41`), and
    FR-003 permits them;
  - the raw-parameter strings;
  - lazy NUL-terminated name copies, which cost nothing unless read.
- **NaN fill**: the caller-buffer path writes O(m + n + k) NaN values and allocates nothing. It is
  justified in Complexity Tracking (plan.md:303).
- **Environment reuse**: reuse is the point of the handle. Model modification without a reload
  does not exist in the Rust API, a gap the spec Assumptions record; this feature does not touch
  it.
- **Solver configuration audit**: research R9 covers the only new parameter, `SoftMemLimit`. It
  is unset by default and confirmed against the vendor default above. The problem data profile is
  unchanged, so the audits of features 001 to 003 stand.
- **Validation**: no validation is removed.

**II. Testing, benchmarks and behavioural evidence: complies (planned).**
- **Test tiers**: the plan names the narrowest test in each tier (plan.md:100-102). The C tests
  reuse the shared harness (`toy.rs`, `compare.rs`, new `cdata.rs` and `ccompiler.rs` in
  `tests/common/`).
- **Fixtures**: no new fixtures; the feature-003 toy instances and `iDopaNeuroC_problem_LP` are
  declared in `project.yml`.
- **Failing-input tests**: every C-layer check has one (plan.md:103-107; contract lines 120-132).
- **Benchmarks**: the plan states benchmark criteria (spec SC-002, SC-003).
- **Behavioural integration**: the C programs are linked against the libraries Cargo built and
  run as separate processes, so they are real callers (plan.md:110-111, 245-248).
- **Comparison rule**: one new function in the owner `compare.rs`. Keeping `judge` for
  cross-solver use is justified because that rule differs (research R7).
- See observations O4 and O5.

## Observations (not violations; route to task generation or closeout)

- **O1. Naming in the contract (XII-C, XII-A).**
  - `optsolver_csc` carries generic fields `m, n`. When it describes F, the field `m` holds k, and
    when it describes Q, it holds n. This mirrors the Rust `CscRef::new(m, n, …)`
    (`src/problem.rs:54-75`), which already reads as "a borrowed m-by-n matrix" for A, Q and F, so
    I do not judge it a new reuse. However, ABI 1.0 freezes it, and renaming later is a major
    version change.
  - The accessor prototypes name their parameters `r` (result) and `c` (capabilities); `c` is
    also the objective field of `optsolver_problem`.
  - Recommend that tasks rename the struct fields to `rows` and `cols`, and the parameters to
    `result` and `caps`, before the header is written. Parameter names do not affect the ABI.

    maintainer.
