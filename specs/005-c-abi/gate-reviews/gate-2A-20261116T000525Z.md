## Findings per principle

### I. Performance And Memory First

**Defect (finding 2).**

What conforms:
- The input path copies nothing. Each array becomes a slice through `slice::from_raw_parts`
  (plan.md:67-71).
- The C layer allocates only:
  - the cone descriptors, linear in `num_cones`;
  - the raw-parameter strings;
  - the result names, copied lazily on first read.
- NaN-filling costs O(m + n + k) writes and is listed in Complexity Tracking (plan.md:282).
- Environment reuse is the purpose of the handle.
- The solver configuration audit is research R9: the only new parameter is `SoftMemLimit`, unset
  by default.

What does not conform: the plan adds one process-wide mutex on the Gurobi load path and does not
justify its effect on wall time. Principle I says: "Every design choice on a load, solve or result
path MUST be justified by its effect on wall time and peak resident memory". Two facts from the
source:
- **The lock covers whole loads.** On the 32-bit index path, `GRBXloadmodel` loads every column of
  A in one call (src/gurobi/load.rs:6-9, 336-375). Research R3 puts every `GRBXloadmodel` under the
  lock. Two threads loading on different environments are therefore serialised for their entire
  load. Research R3 (research.md:81-82) says only "no lock around optimisation, so concurrent solves
  on different environments still run in parallel". That is true of optimisation and not of
  loading.
- **The lock covers licence acquisition.** `GRBstartenv` acquires the licence, and the lock is held
  across it (research.md:63-65, 87-88). One thread's licence check, which may be a network or
  token-server wait, therefore blocks every model creation and every model drop
  (`GRBfreemodel` in `Drop`) on every other thread.

The wall-time criterion (SC-003) is measured single-threaded, so it never sees contention. The
Constitution Check bullet for Principle I (plan.md:49-57) does not mention the lock.

### VII. Rust And FFI Coding Standards

**VII-A conforms.**
- Unsafe code is confined to `src/capi/`, which carries `#![allow(unsafe_code)]` under the crate's
  `#![deny(unsafe_code)]` (src/lib.rs:7). This is the pattern of src/mosek/mod.rs:4, and it
  compiles, because `deny`, unlike `forbid`, can be overridden.
- Every block will carry `SAFETY` comments and every public unsafe function a `# Safety` section.
- `#[unsafe(no_mangle)]` is the correct form for edition 2024.

**VII-B: defect (finding 1).**
- The handles are boxed and freed only by their free functions. That conforms.
- `Send` without `Sync` is supported by the vendor quotations I re-verified. The MOSEK evidence is
  about tasks, plus the §10.6 statement that several threads may use one environment. That is
  enough for `Send`.
- The inference that a lock can stand in for "the main thread" is marked as an unverified,
  accepted risk (research.md:71-82). That conforms to VII-B and X.

The defect is the planned mechanism that is supposed to make the crate-wide lock rule checkable:
- **The source test cannot see calls through the helpers.** Research R3 (research.md:92-94) says
  the test "fails if any line naming one of the five functions (outside `ffi.rs`) is not inside a
  `lifecycle(` call". Today the five functions are called inside the `pub(crate)` helpers `empty()`
  and `start()` (src/gurobi/env.rs:63-98). Their call lines are not lexically inside any
  `lifecycle(` call. Either the test fails on correct code, or the helpers are exempted. If they
  are exempted, a new unlocked caller of `env::empty()` passes the test, because its line names
  none of the five functions. The existing test at src/gurobi/params.rs:391 is exactly such a
  call. So the check misses the failure it exists to catch.
- **No negative test is planned.** The plan has no case showing that the source test fails on a
  deliberately unlocked call. The existing interface-document check has one
  (`interface_document_check_catches_omissions`, tests/standards.rs:272), and this plan has one
  for the header agreement test. This is the XV-C failure below.
- **Re-entrance is not addressed.** On the `GRBXloadmodel` failure path, `xloadmodel` drops a
  `Loaded` defensively (src/gurobi/load.rs:384-388). That `Drop` will take the lock to call
  `GRBfreemodel`. Constitution III requires the message to be read immediately, so the failing call
  and the message read belong in one locked region. If the drop also happens inside that region,
  the non-re-entrant `std::sync::Mutex` deadlocks or panics. Research R3 handles re-entrance only
  for `Env::new`.

## Verdict

**REVISE_ARCHITECTURE (FAIL).**

The architecture is sound and the names are approved:
- a translation-only `capi` module in the one crate;
- edges only into the core and the backends;
- `Send`, not `Sync`, for both environments, on vendor evidence;
- the memory limit as a solver-independent option;
- ADR-0004 written.

The requirements stand. The delta and plan need the five repairs below before approval.

### Violations and repairs

1. **The Gurobi lock check does not detect the failure it guards (VII-B, XV-C).**
   - *Repair:* make the rule enforceable at the helpers. Two ways:
     - have `empty()`, `start()` and every other function that makes one of the five calls take a
       guard token that only `lifecycle` can construct, so the compiler enforces the rule; or
     - make those helpers private to the locked closure, and add their names to the source test's
       list.
   - State how comments and string literals are excluded from the test.
   - Plan a negative test showing the check fails on a deliberately unlocked call.
   - State how the error path of `GRBXloadmodel` reads the message and drops a defensively created
     model without taking the lock twice (src/gurobi/load.rs:384-388).
2. **The lock on the load path is not justified (I).**
   - *Repair:* in the Constitution Check bullet for Principle I, or in Complexity Tracking, state:
     - the uncontended cost of the lock;
     - that contended single-call loads (32-bit indices) and model drops are serialised, and that
       creation waits on `GRBstartenv` licence acquisition.
   - Either justify that, or narrow what the lock covers.
   - Correct research.md:81-82 so it does not imply that loading runs in parallel.
3. **Duplicated buffer validation left in place without a record (V, XIII-C).**
   - *Repair:* either record in *Duplication left in place* that the `solve_into` buffer-length
     checks are duplicated in the two backends (src/gurobi/solve.rs:56-91, src/mosek/solve.rs:55-75)
     and why they stay duplicated (for example ADR-0002 decision 2);
   - or extract one length check into `core.result` that both backends call, and update the delta
