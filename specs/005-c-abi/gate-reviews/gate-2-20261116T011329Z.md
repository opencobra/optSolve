## Violations (each must be repaired; a new fresh-context reviewer then reviews)

### V1. The leak check cannot cover the objects User Story 5 names, and its positive control cannot run in its tier

Principles: II ("Every behavioural change MUST include the narrowest practical check"); XV-C and
XIV-D (a null finding needs an engaged mechanism); Development Workflow ("each user story MUST be
independently testable").

What the spec requires:
- spec.md:278-280 (User Story 5, acceptance scenario 5): "Given every object the library
  allocates (environment handle, result, error message), When the caller frees it with the
  matching free function, Then no memory is leaked".
- User Story 5's Independent Test (spec.md:261-262): "tests run under a leak checker free every
  library-owned object".

What the tasks plan:
- The only leak check is in T016, `tests/c/errors.c`, marked "(unlicensed)" (tasks.md:172).
- Research R7 places the leak check on "the C error-path program" in the unlicensed tier
  (research.md:217-219), and quickstart.md:6-7 likewise.

Why this fails:
- Without a licence, no environment handle or result object can ever be allocated:
  - `optsolver_env_create` fails, either with the solver error or as unsupported (contract:170,
    268-270).
  - Every solve needs an environment.
- So the leak checker never sees the two library-owned objects acceptance scenario 5 names first.
- The positive control, "the same program built with one deliberate unfreed result"
  (tasks.md:179-181), needs a successful solve. Where no licence is present it cannot leak a
  result, so the control would report nothing and the check would be uninterpretable.
- The analysis overstates coverage: implementation-review.md:49 maps "Ownership (FR-016)" to
  "T016 (leaks …)".

Repair (in tasks.md, implementation-review.md and, for consistency, quickstart.md):
- Keep the unlicensed leak check on `errors.c`, with an unlicensed positive control, for example
  one deliberately unfreed `optsolver_last_error_message` copy.
- Add a licensed leak-checked run of the C driver that creates and frees an environment handle,
  solves on the owned path, reads every accessor, and frees the result and a capabilities
  object. Give it its own positive control: one deliberately unfreed result. Vendor-internal
  allocations may need a recorded suppression list, with each suppression justified.
- If the licensed run proves impractical, record that part as unverified, with the reason, at
  closeout.
- Correct the FR-016 and SC-006 coverage rows.
