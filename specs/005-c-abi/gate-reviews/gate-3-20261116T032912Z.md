## Findings per principle

- **Input path**: no copy. `borrow` (`src/capi/problem.rs:189-209`) builds slices over the
  caller's pointers. The pointer-identity tests `every_slice_is_the_callers_array` and
  `sense_form_q_and_conic_slices_are_the_callers_arrays` (`problem.rs:686`, `:727`) cover every
  input array.
- **Allocations**: the only allocations in proportion to the input are justified:
  - the cone list (`cones`, `problem.rs:275-319`), plan line 50;
  - NaN-fill, C-string copies of names and the test-support entry points, all in plan Complexity
    Tracking (`plan.md:305-311`).
- **Heap**: the bundles at `f4af454` show a 0 B difference on the owned path and a lower peak on
  the buffer path, for both backends (N = 3).

  `t012_reuse` passes.
- **Solver configuration audit**: the only new parameter is `SoftMemLimit`. It is set in the single
  writer (`src/gurobi/params.rs:242-246`), with the rationale (research R2). MOSEK rejects the
  field as unsupported.

### II. Testing, Benchmarks, And Behavioural Evidence — violations V-1, V-2

What complies:

  - with `capi` only, `c_interface` runs 15 tests and ignores 20 licensed trials visibly with the

**V-1, failing-input tests missing (II).** II requires a failing-input test for every invariant
checked before an FFI call. Several checks the C layer makes before the first vendor call have no
failing-input test anywhere in `tests/` or `src/capi/` (searched for each message and field name):

- The misaligned-pointer rejection:
  - `borrow`, `src/capi/problem.rs:203-205`, used for every input array;
  - `out_array`, `src/capi/result.rs:241-243`, used for every output buffer.
- In `out_array`:
  - NULL with a nonzero length (`result.rs:231-236`);
  - the byte-size bound `len · 8 ≤ isize::MAX` (`result.rs:238-240`).
- `buffers.struct_size` below the minimum (`result.rs:271-283`).
- The tri-state option flags `options.solver_log`, `options.array_outputs` and
  `options.verification`: a value other than −1, 0 or 1 (`problem.rs:461-467`, `:547-555`).
- `options.certificates` other than 0 or 1 (`problem.rs:556-566`).
- A NULL raw-parameter name or string value (`utf8`, `problem.rs:450-453`). The non-UTF-8 case is
  tested; the NULL case is not.

My probe shows these guards fire correctly, so the defect is the missing test, not the behaviour.
Two of the untested guards fall under the contract's own list, which says "Each check has a
failing-input test" (`contracts/c-interface.md:122-135`):

- "a NULL pointer with a nonzero length", for the output arrays;
- "`struct_size` below the minimum", for `optsolver_buffers`.

So task T006's ticked claim that "every C-layer check of the contract fails with INVALID … naming
the field" overstates the coverage for those items. The misaligned-pointer rejection is not in the
contract's list of C-layer checks, which says the C layer adds "only" the listed checks. It is also
absent from the header and from `docs/llm-interface.md`. That is a contract and documentation
divergence the closeout reconciliation (XIII-D) does not report.

**V-2, the regression check is no longer recorded (II).** II says a regression against recorded
results blocks the feature. Review 1 (its finding V-6) required the Rust-path regression comparison
against feature 003's bundle to be recorded.

- It was recorded only in the first receipt's edited Tests section at `a9c3173` (lines 70-74 there:
  "… solve medians 22.6 / 30.8 ms against 29.4 / 29.2 ms (N = 5 each) — no regression").
- Review 2's repair restored that receipt to its `11647b1` text, which removed the record.
- The new repair receipt does not carry it.
- `human-loop.md:101` still says "default benchmark ok (regression comparison as in the repair
  receipt)". That pointer is false.
- The default benchmark at `f4af454` (`20261116T032133Z-bench`) has not been compared with feature
  003's bundle in any committed artefact.

The data does not show a regression of a criterion:

- heap peak during load: 78 536 B in all three bundles;
- the overhead criterion (limit 0.05) passes in all three bundles: 0.023 and 0.018 here, against
  0.018 and 0.018 (Gurobi / MOSEK, `LP`, `usize`).

But the validation sub-phase medians move between 7.5e-5 s and 1.6e-4 s across the three sessions
on validation code this feature did not change. So the comparison needs its reading stated, not
only its numbers.
