## Findings (per principle)

### I. Performance And Memory First: no violation

- The design reuses the environment. The handle acquires the licence once (FR-007,
  spec.md:296-299), and User Story 2 tests this. Inputs are borrowed (FR-003, spec.md:273-277).
  The feature honours the switch that turns array outputs off (FR-004 lists "array outputs").
- The modify-and-re-solve requirement is not met by the Rust API yet. The spec does not hide
  this: it records it as an assumption with a later minor version (spec.md:438-439). The feature
  does not worsen the gap.
- The solver configuration audit happens at the plan stage. The spec adds one mapping,
  `memory_limit_gb` to `SoftMemLimit`, and sets it only on request, so it imposes no default.
- Observation for the plan: FR-003 lets the C layer build cone descriptors, and the plan must
  state their size (spec.md:276-277).

### II. Testing, Benchmarks, And Behavioural Evidence: VIOLATION (finding F3)

- The two test tiers are stated (FR-014, spec.md:331-336). Benchmarks with wall-time and memory
  targets are acceptance criteria on a named instance (SC-002 and SC-003, spec.md:393-403). I
  checked the instance against `docs/test-corpus.md:23,67`: m = 1344, n = 2942, nnz = 13748. The
  memory-limit option is shown to reach a real caller (SC-005).
- **F3, a tolerance that does not exist.** SC-001 (spec.md:387-392), FR-014 (spec.md:333-335)
  and User Story 1's independent test (spec.md:88-92) require every returned vector to agree
  "within the tolerance the cross-solver comparison already uses for same-backend runs" or "by
  the comparison rules already used for cross-solver tests".
  - The existing rule compares only status, objective and verification verdict:
    `tests/common/compare.rs:83-115` (`judge`) and `tests/common/toy.rs:201-205`
    (`objectives_agree`). There is no vector rule and no "same-backend" rule.
  - The acceptance criterion for x, y, z, z_l, z_u, s and row activity is therefore undefined.
    This breaks the requirement that numerical comparisons use tolerances justified by the
    solver's own tolerances, and the requirement that requirements be testable.
  - **Repair**: state the vector rule in the spec. For example: bit-identical for same-backend,
    deterministic runs with the same effective parameters; otherwise a named tolerance derived
    from the solver's feasibility and optimality tolerances. Then correct the claim that an
    existing rule covers vectors.
- Observation for the plan: Principle II requires a failing-input test for every invariant
  checked before an FFI call. The C layer adds invariants of its own, such as null pointers,
  negative 32-bit indices, invalid sense characters, invalid cone-kind and option codes, and
  version mismatch. SC-006 covers only "the existing Rust failing-input tests", so the plan must
  add C-specific failing-input tests. User Story 5 scenario 1 already names some of them.

### III. Bounded Diagnostics And Preserved Statuses: no violation

- FR-018 (spec.md:351-352) forbids writing to standard output or standard error.
- The raw status codes are returned (FR-005), and solver errors carry the vendor's code and
  message (FR-010).

### IV. Zero-Copy Borrowed Inputs And Bulk Native Calls: no violation

- No copy is made at the C boundary (FR-003).
- Both native row-index widths are accepted. This matches `RowIndex` for `usize` and `i32`

- Both row-bound forms are accepted (FR-002).
- The backend can write into caller-supplied buffers (FR-006), mirroring `solve_into` and
  `SolutionBuffers` (`src/result.rs:295-313`).

### V. Spec-Driven Scope Control And Reuse: no violation

- FR-001 (spec.md:260-264) forbids re-implementing validation, status translation, parameter

- The only Rust API change is the memory-limit option. Finding F4 qualifies this.
- Observation: the two test-support entry points (spec.md:447-449) are new public surface. The
  plan should justify them and say whether they ship in release builds.

### VII. Rust And FFI Coding Standards: VIOLATION (finding F4)

- VII-C, statuses and panics: the memory limit is a status (FR-011), and panics are contained
  (FR-009). VII-G, one location for parameters: the memory limit is a shared option, it conflicts
  with `SoftMemLimit` set by the raw route, and `MemLimit` stays reachable (spec.md:47-52, FR-011).
  This is consistent with `src/options/check.rs`.
- **F4, the thread rule and `Send`.**
  - FR-008 (spec.md:300-304) lets an environment handle be used from a thread other than the one
    that created it. In Rust terms that means the environment is `Send`.
  - Today `Env` is neither `Send` nor `Sync`. No `unsafe impl Send` exists in `src/`. This was a
    recorded decision, R15 in `specs/001-core-gurobi-lp/research.md:237-241` ("Making them
    `Send` waits for the vendor documentation check (constitution VII-B)"), repeated in
    `specs/002-mosek-lp-qp-clp/research.md:33-34`, and documented to callers in
    `docs/llm-interface.md:254-257`.
  - The spec neither names this ruling nor says whether the Rust `Env` becomes `Send`.
    Meanwhile FR-021 (spec.md:359-361) says "the only Rust-API change is the memory-limit
    option".
  - So either the Rust API changes in a way the spec does not declare, or the C layer moves a
    non-`Send` type between threads without the documented `Send` that VII-B requires. The
    vendor evidence is now cited, which is what R15 waited for. The decision is probably
    correct; it is not recorded as superseding the earlier ruling. That breaks VII-B and also
    XV-E: "Overriding a control is sometimes right and never silent: record the grounds."
  - **Repair**: in the Clarifications thread answer and FR-008, say that the decision supersedes
    R15 of feature 001, R2 of feature 002, and the Threading section of the interface document.
    State whether the Rust `Env` types become `Send` (not `Sync`), citing the vendor
    documentation as VII-B requires, and if so add that to FR-021's list of Rust API changes and
    to FR-019's update of the interface document.
- Observation for the plan: Cargo's `crate-type` cannot be switched by a feature. The plan must
  show how FR-012 ("behind an additive Cargo feature") delivers the static and shared libraries,
  for example through `cargo rustc --crate-type`, and how it meets VII-F (the `links` key, build
  script environment variables).

6. **F6** (XII-C, Notation): M and N are used for version numbers in FR-015, and N is already the
