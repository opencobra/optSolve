## Findings per principle

### I. Performance And Memory First — satisfied

- **Input path, no copy.** `plan.md:50-58` and research R5 (`research.md:153-156`) say every input
  array is borrowed. The C layer allocates only two things:
  - the cone descriptor vector, including the power-cone exponents, which are copied into
    `Cone::PrimalPower { alpha: Vec<f64> }` (`src/conic.rs:30-42`);
  - the raw-parameter `String`s, which the Rust API itself requires (`Options::raw:
    Vec<(String, ParamValue)>`, `src/options.rs`).

  Both are O(number of cones or parameters), within the O(rows + cols) allowance. Nothing is
  proportional to nnz.
- **Result path.**
  - `Vec`s are read in place.
  - Names are converted lazily, on first read (`research.md:157-165`), so names cost nothing
    unless read.
  - Caller buffers get O(m + n + k) NaN writes. These are listed in Complexity Tracking
    (`plan.md:301`) with the rejected alternative.
- **Environment reuse and modification.** Environment reuse is the purpose of the handle.
  Modification without reload does not exist in the Rust API, and this is stated
  (`spec.md:507-508`).
- **Outputs.** Every output the Rust result carries can be reached from C. I checked each field of
  `Solution` (`src/result.rs:151-197`) against the contract accessors
  (`contracts/c-interface.md:200-229`): status, limit reason, returned, every array, basis,
  objective, bound, both counts, four timings, certificate, raw statuses, identity, attributes,
  effective parameters and verification.
- **Solver configuration audit** (R9, `research.md:233-236`). The only new parameter is
  `SoftMemLimit`, unset by default. I checked its vendor default (Infinity) in the 13.0 parameter
  reference. No problem profile changes.
- **Targets.** The heap and wall-time criteria (SC-002, SC-003) are measured against the Rust path
  on the same machine.
